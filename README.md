# FurkVPN для Windows

Клиент FurkVPN для Windows 10 и 11 (x64) на Xray-core. Функции те же, что в Android-приложении
([furkvpn-android](https://github.com/foxodever/furkvpn-android)), вид тоже: Material 3, его цвета и шрифт Google Sans.
Сервер общий: furkapp.net (API `/api/v1/config`, страница `/import`, загрузки).

```
cmd/furkvpn/           FurkVPN.exe — окно (Wails + WebView2) и значок в трее, работает от имени пользователя
cmd/furkvpn-service/   FurkVPNService.exe — служба Windows (LocalSystem): ядро Xray, TUN, вся логика
internal/              общий код: ключи, подписка, маршрутизация, белые списки, сборка конфига Xray, движок службы
frontend/              интерфейс (Svelte 5, TypeScript), встраивается в FurkVPN.exe
installer/             установщик (NSIS)
build/                 сборка, значки, ресурсы Windows, выкладка
cmd/devbridge/         разработка: интерфейс в обычном браузере поверх службы, запущенной на Linux
```

## Как это устроено

- **Две программы.** VPN требует прав администратора (адаптер, маршруты, фильтры Windows), поэтому всё, что с ним
  связано, делает служба `FurkVPN`. Её ставит установщик, и она запускается вместе с Windows. Окно (`FurkVPN.exe`)
  работает без прав администратора, поэтому UAC при запуске не спрашивает. Они общаются по именованному каналу
  `\\.\pipe\FurkVPN`: JSON-строки, запросы-ответы и события. Служба отдаёт состояние частями (`vpn`, `traffic`,
  `subscription`, `routing`…) и присылает только те, что изменились. Права на канал: система и администраторы —
  полные, вошедшие в систему пользователи — чтение и запись, но не создание экземпляров канала. Окно проверяет, что
  канал создан системой (владелец SYSTEM или «Администраторы», сеанс 0): программа без прав не может выдать себя за
  службу, пока та остановлена.
- **Ядро** — Xray-core v26.10.21, как в Android (с 1.6.1) и iOS: в нём исправления клиента Hysteria, новый лёгкий
  сетевой стек TUN вместо gVisor и защита собственных соединений Xray от «weak host send» в Windows. До 1.3.0 было
  v26.9.30 (v26.9.9, на которую Android откатывался в 1.4.1, для Windows не подходила: в ней нет фильтров утечек и
  пропуска DNS-серверов адаптера). Используется встроенный TUN-вход Xray для
  Windows (Wintun): адаптер `FurkVPN` (172.19.0.1/30, fdfe:dcba:9876::1/126), маршруты — всё адресное пространство,
  а при «Локальной сети напрямую» (по умолчанию) без домашних сетей (10/8, 172.16/12, 192.168/16), link-local,
  мультикаста и широковещания: 39 префиксов IPv4 и 9 IPv6 (`internal/xrayconf/tunroutes.go`, порт TunRoutes из
  Android 1.7.1), так что обнаружение устройств, принтеры и сети за роутером работают как без VPN
  (`autoSystemRoutingTable`). Собственные соединения Xray привязаны к физическому интерфейсу
  (`autoOutboundsInterface`), иначе они бы зациклились в туннеле. Фильтры Windows Filtering Platform
  (`autoSystemWfpBlockLeak: ["dns"]`) не дают DNS-запросам уйти мимо туннеля: Windows шлёт их на DNS-серверы всех
  адаптеров, а программы ходят к роутеру по маршруту локальной сети. DNS-сервер адаптера — 172.19.0.2, запросы на
  порт 53 отвечает DNS-модуль Xray, как на Android (по TCP, `serveStale`, только IPv4).
- **Конфиг** берётся из подписки Remnawave (`<ключ>/json`) как есть: правила, балансировщики автовыбора, burstObservatory.
  Меняется только вход (TUN и раздача вместо socks/http шаблона). Секции, которые могли бы открыть порт или писать
  файлы от имени SYSTEM (`api`, `metrics`, `reverse`, логи), выбрасываются.
- **Программы без VPN** — правило маршрутизации Xray `process` (по имени exe). Оно стоит раньше остальных, так что
  на эти программы не действуют ни правила сервера, ни свои. Рекомендуемые исключения для Windows приходят из API
  отдельным списком: `/opt/furkapp/config/config.json` → `app.windows.defaultExcludedApps`, имена процессов
  (`["chrome.exe", "Telegram.exe"]`; `.exe` можно не писать, регистр не важен). Сервер подхватывает файл сам, приложения —
  при запуске (если загружали больше часа назад), раз в 6 часов и по «Проверить обновления». На Android список `defaultExcludedApps` состоит из пакетов. Список программ на
  экране собирается из ярлыков меню «Пуск» и запущенных программ, с их значками; любую программу можно выбрать файлом .exe.
- **Только выбранные программы через VPN** (1.4.0) — второй режим того же экрана, со своим списком (`vpnApps` в
  настройках; список программ без VPN и рекомендуемые исключения ждут возврата в обычный режим). У правил Xray нет
  «все, кроме», поэтому соединения выбранных программ уходят в `loopback` и возвращаются в маршрутизацию от входа
  `apps-in`, где действуют свои правила и правила сервера (loopback смотрит в соединение ещё раз: правила шаблонов
  ловят протокол — BitTorrent, QUIC). Всё остальное с этого компьютера идёт напрямую. DNS Windows спрашивает от имени
  своей службы, поэтому он работает как в обычном режиме. Файл со списком программ хранит оба списка и режим.
- **Расширенные настройки** (для тех, кому надо). Режим TUN: MTU (1280–9000, по умолчанию 1500), IPv6 через VPN
  (выключен — у адаптера нет IPv6 и маршрута `::/0`, а IPv6 мимо туннеля закрыт фильтром `misconfigtun`, программы
  переходят на IPv4), защита от утечек DNS (`autoSystemWfpBlockLeak: ["dns"]`; без неё DNS-серверы роутера и рабочей
  сети снова доступны). Режим TUN можно выключить: адаптера нет, VPN — прокси на 127.0.0.1:10808 (SOCKS5 и HTTP на
  одном порту, если занят — следующий свободный). «Системный прокси» (по умолчанию включён) прописывает его в настройки
  прокси Windows текущего пользователя, пока VPN включён. Это делает окно, служба не может менять настройки
  пользователя. Прежние настройки окно запоминает в `ui.json` и возвращает при отключении, выходе, следующем запуске
  после сбоя; установщик и удаление тоже их возвращают (`FurkVPN.exe --restore-proxy`). Программы без VPN и журнал
  подключений работают и через прокси. Изменения применяются сразу, VPN переподключается сам.
- **Белые списки** — как на Android: проверка сайтов из `whitelist.*` мимо VPN (сокеты привязаны к физическому
  интерфейсу), при открытом окне, смене сети и раз в 5 минут при подключённом VPN. Автопереключение на
  «Автовыбор LTE» и обратно работает по тем же правилам.
- **Автовыбор**: перезапуск ядра при смене сети (в том числе когда та же сеть пропала и вернулась), раз в 10 секунд
  проверка серверов, которые нёс автовыбор, после сна дольше 5 минут — перепроверка, запасной сервер (`fallbackTag`) —
  всё как в Android 1.3–1.5.
- **Пинг** (как в Android 1.5.0) — время подключения к серверу и запроса к сайту проверки через него: адрес из
  JSON-конфига (`burstObservatory.pingConfig.destination` или `observatory.probeURL`), если его нет — `delayTestUrl` из
  API. Поиск адреса сервера по имени в пинг не входит: имена резолвятся заранее (через DNS-сервер конфига, у которого
  этот домен в списке, — в шаблоне это 77.88.8.8, — иначе через DNS Windows; пока VPN включён, эти запросы привязаны к
  физическому интерфейсу, как собственные соединения Xray), и тестовое ядро подключается к IP. Имя сервера остаётся
  SNI и Host, если они не заданы. «Автовыбор» тоже получает пинг: запрос идёт через его маршрутизацию и балансировщик.
  Правый щелчок по серверу или «Автовыбору» проверяет только его — сразу, даже если он ждёт в очереди общего пинга.
  Кнопка пинга во время проверки не выключается: повторное нажатие начинает заново (как в Happ и Android 1.6.2),
  начатые замеры дорабатывают, ограничение «шесть одновременно» общее. До 1.2.0 серверы с доменом показывали ~4 с.
- **Hysteria 2**: Remnawave пишет смену портов по-старому (`finalmask.quicParams.udpHop`), а ядро понимает только маску
  `udphop`, последней в `finalmask.udp`. Служба переписывает старую форму при подключении и для пинга
  (`internal/core/hysteria.go`, из Android 1.6.0). В списке такие серверы подписаны «HYSTERIA2 · QUIC».
- **Общее состояние Xray**: DNS-клиент и менеджер исходящих, через которые ядро подключается к серверам по имени, у
  Xray одни на процесс, и каждое новое ядро забирает их себе. Тестовое ядро пинга оставляло работающему VPN свой, уже
  закрытый DNS: новые подключения к серверам с доменом ждали 4 с, а проверки автовыбора (3 с) считали их упавшими.
  Теперь после создания тестового ядра это состояние возвращается работающему (`TestDelayTestLeavesTheRunningInstanceItsDNS`).
- **Память службы** (1.3.1): Xray рассчитан на одно ядро на процесс, а здесь каждый пинг — отдельное ядро, и ядро VPN
  пересоздаётся при смене сети, настроек и сервера. Из-за этого служба росла: в 1.3.0 пять «пингов всех» давали
  +60 МБ и +300 дескрипторов, и обратно это не уходило. Теперь после пингов служба за 2 минуты возвращается к
  исходному размеру. Что сделано:
  - Соединения gRPC и XHTTP Xray складывает в две таблицы, общие на процесс, и не убирает их оттуда, когда ядро
    закрыто: соединения оставались открытыми, а каждая запись держала в памяти всё закрытое ядро вместе с его
    маршрутизацией. `closeInstance` (`internal/core/dialers.go`) закрывает ядро и убирает его записи. Таблицы и три
    поля не экспортированы, до них добираемся через `go:linkname` и reflect. **После обновления Xray запускать
    `TestClosedInstanceLeavesNoConnections`**: если Xray их переименует, чистка молча перестанет работать, а этот
    тест упадёт.
  - Сервер, который принял соединение и молчит (например, пересылка, у которой дальний конец умер), оставлял Xray
    ждать TLS-рукопожатие вечно: таймаута там нет, отмена запроса до рукопожатия не доходит, а XHTTP ставит за ним
    в очередь все следующие запросы. Автовыбор проверяет каждый сервер несколько раз в минуту, так что с одним таким
    сервером в списке зависшие соединения копились всё время, пока VPN включён. Теперь соединение с портом сервера
    за TLS или REALITY, по которому что-то отправлено и за 15 секунд не пришло ни байта, обрывается
    (`internal/core/silent.go`; счётчики сокета — `SIO_TCP_INFO` в Windows, `TCP_INFO` в Linux). Прямые соединения
    программ и серверы без TLS не трогаются: там молчание сервера может быть нормой.
  - Пинг больше не оставляет после себя то, что Xray ещё делал для запроса: у измерения свой контекст, он
    отменяется вместе с ним.
  - Каждый DNS-запрос программы (у каждого свой порт) Xray держит как соединение, пока оно не простоит `connIdle`
    своего уровня политики: по умолчанию 300 секунд, а из-за способа отсчёта до 600. У DNS-исходящего теперь свой
    уровень (`policy.levels.53`, `connIdle` 10 секунд, `xrayconf.DNSLevel`), остальные соединения живут как раньше.
    Если панель сама задала DNS-исходящему `userLevel`, он остаётся.

  Диагностика: запрос `memory` по каналу службы отдаёт число горутин и размер кучи, с `{"profiles": true}` ещё
  пишет `goroutines.txt` и `heap.pprof` в папку журналов. `cmd/leaktest` гоняет на Linux пинги по кругу, конфиг
  как VPN или автовыбор по молчащим серверам и печатает те же числа.
- **Windows без IPv6** (1.3.2): если IPv6 выключен на всю систему (`DisabledComponents` в реестре — обычный совет
  «отключите IPv6»), у нового адаптера IPv6 нет вообще. Xray, которому сказано настроить адаптеру адрес и маршрут
  IPv6, 15 секунд повторяет попытку и сдаётся: «Ошибка подключения: start xray: … failed to start proxy > Element
  not found». Теперь перед запуском служба смотрит, есть ли IPv6 хоть у одного адаптера, кроме петлевого и туннельных
  (`netx.HasIPv6`), и если нет — собирает адаптер без IPv6, как при выключенной настройке «IPv6 через VPN». Если IPv6
  в системе есть, а адаптер всё равно не поднялся с этой ошибкой, ядро запускается второй раз без IPv6, и служба
  помнит это до перезапуска (`Engine.noTunIPv6`), чтобы не ждать 15 секунд при каждом подключении. Галочка IPv6,
  снятая только у сетевой карты, ничего не меняет: новому адаптеру Windows IPv6 даёт.
- **Повреждённый драйвер адаптера** (1.4.4): если Windows числит драйвер Wintun установленным, а файла
  `System32\drivers\wintun.sys` нет (удалил антивирус, «чистильщик» или установщик другого VPN), адаптер создаётся,
  но не запускается, и каждое подключение через 15 секунд кончалось ошибкой «start xray: … failed to start proxy >
  The system cannot find the file specified». Сам Wintun драйвер не переустанавливает: видит его в хранилище
  драйверов («Using existing driver»). Теперь, если адаптер не поднялся (`core.AdapterFailed`: голая ошибка Windows
  сразу под «failed to start proxy»), служба убирает драйвер из хранилища (`core.ReinstallAdapterDriver`,
  `WintunDeleteDriver`) и запускает ядро ещё раз — Wintun ставит драйвер заново из `wintun.dll`. Пока драйвером
  пользуется адаптер другой программы, он не удаляется. Если не помогло, окно говорит об адаптере по-русски и советует
  перезагрузку или выключить «Режим TUN», а не показывает цепочку ошибок Xray. Сообщения самого Wintun (например,
  `Failed to setup adapter (problem code: 0x27, ntstatus: 0xC0000034)`) теперь попадают в `service.log` с пометкой
  `lib:` — раньше служба их теряла. До 1.4.4 чинится вручную, PowerShell от администратора:
  `Get-WindowsDriver -Online | ? OriginalFileName -like '*wintun.inf' | % { pnputil /delete-driver $_.Driver /uninstall /force }`,
  затем подключиться снова. `cmd/tuntest` включает и выключает адаптер много раз подряд без сервера (`-v` — сообщения
  Wintun, `-repair` — чинить драйвер, как служба).
- **Подписка**: обновление ждёт начатую загрузку ключа и берёт ключ уже после неё, так что не возвращает старый ключ
  поверх только что добавленного; плановое обновление не качает подписку второй раз, если её только что обновили.
  `subscription_configs.json` хранит `fetchedAt` списка, к которому относятся конфиги: если служба остановилась между
  записью двух файлов, конфиги не сопоставляются с чужим списком — ключ остаётся, подписка скачивается заново.
- **Заголовки и проверки**: в заголовках к панели только печатные ASCII (имя устройства вроде «Box™» иначе уходило как
  есть); проверки белых списков (vk.ru, ya.ru, Google мимо VPN) идут без User-Agent FurkVPN.
- **Домены ключей**: ключ принимается, если его домен в `allowedSubscriptionHosts` из API. Если домена там нет, а
  настройки не обновлялись последнюю минуту, служба сначала заново запрашивает их (настройки могли ещё не прийти
  после установки или прийти до добавления домена) и только потом пишет «Это не ключ FurkVPN». Встроенный запасной
  список (на случай, когда furkapp.net недоступен) с 1.3.1 содержит все домены подписок, а не только `*.furkvpn.com`
  и furkconnection.net: до этого ключ furkgateway.com на свежей установке мог оказаться «чужим».
- **Ошибки службы в окне**: Wails передаёт интерфейсу `new Error(значение)`, поэтому ошибка отдаётся JSON-текстом —
  до 1.3.0 объект превращался в «[object Object]», и вместо «Это не ключ FurkVPN» окно показывало общую ошибку.
- **Домены серверов вне списка DNS**: если у DNS-сервера конфига есть список доменов серверов, а какого-то сервера в
  нём нет, служба дописывает его туда (при подключении и для пинга), иначе его имя резолвилось бы через прокси.
- **Продлить / Купить тариф** в карточке подписки: «Продлить», когда до конца тарифа меньше 2 дней или он закончился,
  на бесплатном тарифе — «Купить тариф». Обе открывают `https://<site.domain>/renewal?sub=<id подписки>`.
- **Прокси для Telegram** — кнопка под «Наш сайт / Наш бот / Поддержка» открывает список из API (`telegramProxies`);
  щелчок отдаёт ссылку Telegram (`tg://`) или браузеру (`https://t.me/…`). Пока список пуст, кнопки нет.
- **Раздача интернета**: HTTP-прокси и SOCKS5 на 0.0.0.0 (8080/1080 или следующие свободные), только для адресов
  локальных сетей. На время раздачи служба добавляет правило брандмауэра Windows для своих портов.
- **Журнал подключений**: программа определяется по таблицам TCP/UDP Windows (как правило `process` в Xray), её
  название — из свойств exe. Программы без VPN тоже видны, с пометкой «Напрямую».
- **Ссылки и файлы**: установщик регистрирует протокол `furkvpn://`. Страница furkapp.net/import на компьютере
  открывает `furkvpn://import?url=…`, так что вход через бота и через сайт работает без изменений на сервере.
  В тексте с несколькими ссылками (сообщение бота: t.me, сайт, ключ) берётся первая, которая является ключом.
  «Войти через сайт» сразу открывает личный кабинет (`/dashboard/install`), без выбора «по почте».
- **Телевизор**: Настройки → «Подключить телевизор» — код из 6 символов с экрана FurkVPN на Android TV отправляет ключ
  этого компьютера на телевизор (`POST /api/v1/tv/send`). Набранное в русской раскладке переводится в латиницу по
  клавишам («РГ ЯОА» → «HUZJF»). Ссылки телевизора `furkapp.net/tv/<код>` и `furkvpn://tv/<код>` открывают то же
  с подтверждением.
- **Вход с телефона по QR-коду** (1.5.0): «Войти по QR-коду» на экране входа и в «Сменить ключ». Компьютер ведёт себя
  как телевизор с FurkVPN: берёт код (`POST /api/v1/tv/session`), показывает его и QR-код ссылки
  `furkapp.net/tv/<код>` и ждёт ключ (`POST /api/v1/tv/wait`, сервер держит запрос 10 секунд). Телефон отправляет
  ключ так же, как на телевизор: «Подключить телевизор» в приложении или страница, которую открывает QR-код, —
  поэтому в приложениях для телефона и на сервере ничего не менялось, а телефон называет компьютер телевизором
  (диалог об этом предупреждает). Полученный ключ идёт тем же путём, что вставленный: с вопросом о замене, если
  ключ уже есть. Запросы делает служба (`tvSession`, `tvWait` в `internal/engine/tv.go`), цикл ожидания — в окне
  (`components/PhoneSignIn.svelte`) и только пока диалог открыт; код живёт 15 минут, после чего диалог показывает
  «Код устарел» и новый берёт по кнопке, так что забытое окно не опрашивает сервер. QR-код рисует
  `components/QrCode.svelte` (библиотека qrcode-generator): чёрный на белом в обеих темах.
- **Команды**: `FurkVPN.exe --connect`, `--disconnect`, `--toggle` включают и выключают VPN без окна (ярлыки,
  планировщик заданий, горячие клавиши; если приложение не запущено, оно запускается в трей). Правый щелчок по
  значку FurkVPN на панели задач — «Подключить VPN» / «Отключить VPN» (список переходов Windows) — аналог ярлыков
  Android.
  Файлы настроек (`.json`) открываются через «Открыть с помощью → FurkVPN» или перетаскиванием в окно. Рамка
  «Отпустите файл…» видна, пока файл над окном: до 1.5.0 она оставалась навсегда, если файл пронесли над окном и
  унесли, не отпустив (окно ждало ухода файла с самой страницы, а он уходит с того, что на ней лежит). Теперь уход
  определяется по `relatedTarget`, а если перетаскивание кончилось молча, рамку убирает таймер: `dragover`
  приходит всё время, пока файл над окном. Файл принимает всё окно, открытый диалог тоже.
  Файл маршрутизации тот же, что у Android (`furkvpn-routing`). Список программ — свой тип (`furkvpn-windows-apps`).
- **Трей**: серый значок — не подключено, оранжевый — подключение, зелёный — подключено. Щелчок открывает окно, в
  меню «Подключиться/Отключиться», «Открыть FurkVPN», «Выход» (отключает VPN). Закрытие окна прячет его в трей.
- **Автозапуск**: при первом запуске окно прописывается в автозагрузку пользователя (`--tray`, без окна), это
  выключается в настройках. «Подключаться при включении компьютера» включает VPN службой, ещё до входа в Windows.
- **Обновления**: блок `windows.update` в config.json (`versionCode`, `versionName`, `url`, `sha256`, `changelog`).
  Служба скачивает установщик в `C:\ProgramData\FurkVPN Updates` (писать туда может только система),
  проверяет SHA-256. Окно запускает его с `/S /UPDATE`, Windows спрашивает разрешение (UAC). Установщик тихо
  ставит новую версию и снова запускает окно; если VPN был включён, служба включает его обратно.
  Установщик закрывает только само окно (`taskkill` без `/T`): его запускает окно, и до 1.4.1 он вместе с «окном и
  его дочерними процессами» убивал себя — кнопка «Установить» закрывала программу и ничего не ставила.
- **Тип пинга** (1.4.2): Настройки → «Тип пинга». «Через сервер (GET)» — как раньше и по умолчанию: запрос к сайту
  через сервер. «TCP» — время соединения с портом сервера, «ICMP» — эхо-запрос, как у команды ping
  (`IcmpSendEcho2Ex` с адресом настоящей сети в качестве источника, чтобы запрос не уходил в TUN). Оба меряют сам
  сервер мимо VPN и не говорят, работает ли через него VPN; у автовыбора берётся лучший из его серверов. Сервер на
  UDP (Hysteria, WireGuard, mKCP) по TCP не измерить — для него остаётся пинг через сервер. ICMP — только IPv4.
- **Белые списки без переключения** (1.4.2): «Переключать на LTE-серверы» выключается отдельно от
  «Определять белые списки»: карточка на главном экране и проверки остаются, сервер программа не меняет.
- **Тёмная тема** (1.4.1): Настройки → Интерфейс, «Как в Windows / Включена / Выключена», как на Android. Выбор
  хранит окно (`theme` в `ui.json`), заголовок окна красится так же; страница получает `data-theme` (`lib/theme.ts`).
- **Анимации**: если в Windows выключены «Эффекты анимации», появления и переходы отключаются, а индикаторы
  ожидания (класс `endless`) крутятся с обычной скоростью. До 1.4.1 они ускорялись вместе со всем и мельтешили.
- **Данные**: `C:\ProgramData\FurkVPN` (ключ, подписка, настройки; доступ только у системы и администраторов),
  журналы службы — `C:\ProgramData\FurkVPN\logs` (без посещённых адресов). Окно хранит только размер и
  флажки в `%APPDATA%\FurkVPN\ui.json`, журнал окна — `%LOCALAPPDATA%\FurkVPN\ui.log`.
- **Флаги стран**: Windows не рисует эмодзи флагов (вместо 🇳🇱 показывает «NL»), поэтому в интерфейс встроен шрифт
  Twemoji Country Flags. Остальные эмодзи берутся из системного шрифта.

## Сборка (на Linux)

Нужны Go (`/usr/local/go`), Node.js, `go-winres` (`go install github.com/tc-hib/go-winres@latest`), NSIS (`makensis`),
`osslsigncode`, `curl`.

```bash
build/build.sh        # → dist/FurkVPN-Setup-<версия>.exe (и FurkVPN.exe, FurkVPNService.exe отдельно)
go test ./...         # тесты: ключи, подписка, маршрутизация, белые списки, конфиг Xray, пинг, движок службы, IPC
go run ./cmd/pingtest -sub <подписка.json>   # пинг всех серверов подписки, как кнопка пинга
cd frontend && npm run check   # проверка типов интерфейса
```

Версия — файлы `VERSION` (номер вида 1.3.2) и `VERSIONCODE` (растёт с каждым выпуском, по нему приложение понимает, что
вышло обновление). Wintun 0.14.1 скачивается с wintun.net и сверяется по SHA-256, загрузчик WebView2 — с сайта
Microsoft, сверяется подпись. Сертификата подписи кода пока нет: SmartScreen при первом запуске установщика
покажет «Windows защитила ваш компьютер» → «Подробнее» → «Выполнить в любом случае», а UAC — «неизвестный издатель».

### Интерфейс в браузере

Служба собирается и на Linux: там режим TUN всегда выключен — прокси на 127.0.0.1:10808, сеть сервера не
трогается. `cmd/devbridge` отдаёт интерфейс в браузер и передаёт запросы службе.

```bash
go build -o /tmp/furkvpn-dev-service ./cmd/furkvpn-service && FURKVPN_DATA=/tmp/furkvpn-data /tmp/furkvpn-dev-service &
(cd frontend && npm run build) && go run ./cmd/devbridge -dist frontend/dist   # http://127.0.0.1:34115
```

## Выпуск

```bash
build/build.sh
build/publish.sh "Что нового"   # на сервере furkapp.net: установщик в /download, блок windows.update в config.json
```

furkapp.net открывается через промежуточный сервер, он отдаёт `/download/` со своего диска, а если файла там нет,
берёт его с основного. Новые установщики (`FurkVPN-Setup-<версия>.exe`, `FurkVPN-Setup.exe`) стоит скопировать и туда,
как APK.

Для теста обновлений служба читает переменную `FURKVPN_API` (значение `Environment` службы в реестре) — другой
адрес API вместо furkapp.net. С ней разрешены установщики по http.

## Проверено (виртуальная Windows 11 24H2, русская)

- установка с загрузкой WebView2 (в образе его не было), установка поверх, удаление;
- вход по ссылке `furkvpn://import?url=…` (как со страницы furkapp.net/import) при уже открытом окне;
- подключение: адаптер FurkVPN, маршрут по умолчанию через него, внешний IP — IP серверов автовыбора;
- DNS: запрос напрямую к DNS-серверу роутера не проходит, к 8.8.8.8 отвечает Xray;
- программа без VPN (curl.exe) выходит со своим IP, остальные — через VPN, туннель пересобирается сам;
- раздача: HTTP и SOCKS5 по адресу в локальной сети работают, с 127.0.0.1 отсекаются, правило брандмауэра есть;
- журнал подключений с названиями программ;
- белые списки (Google закрыт через hosts): переключение на «Автовыбор LTE», пинг только обходных, возврат на Wi-Fi;
- адаптер выключен и включён: ядро перезапустилось, интернет через VPN вернулся;
- 1.3.0 (ядро v26.10.21): сайты через VPN за 0,2–0,8 с, 20 МБ за 0,6 с; маршруты: 192.168.x/10.x — Ethernet, у адаптера
  нет мультикаста; DNS к роутеру не проходит; программа без VPN — со своим IP; пинг 47 серверов с перезапуском за 21 с;
  `--connect/--disconnect/--toggle` (и без запущенного окна), задачи на панели задач; «Подключить телевизор» в
  русской раскладке и по ссылке `furkvpn://tv/<код>` — ключ дошёл до тестовой сессии телевизора; устаревший код и
  чужой ключ показывают свои сообщения; без IPv6 и режим прокси работают;
- перезагрузка: служба подключилась сама (автоподключение), окно запустилось в трей;
- трей: цвет по состоянию, меню, подключение из меню, открытие окна;
- обновление 1.0.0 → 1.0.1 через тестовый API: скачивание, UAC, тихая установка, VPN снова включён, окно открылось;
- расширенные настройки: MTU 1400 у адаптера; без IPv6 нет адреса и маршрута `::/0`, IPv6-соединение мимо туннеля
  не проходит; без защиты DNS роутер отвечает напрямую; режим прокси: адаптера нет, системный прокси пользователя
  указывает на 127.0.0.1:10808, программы с системным прокси выходят через VPN, curl — напрямую; прежние настройки
  (с «Определять параметры автоматически») возвращаются при отключении, выключении системного прокси, запуске после
  аварийного завершения и по `--restore-proxy`; сброс возвращает режим TUN;
- 1.5.0: файл настроек пронесён над окном и унесён — рамка пропала (в 1.4.4 оставалась), держится, пока файл
  неподвижен над окном, файл принимается и поверх открытого диалога; вход по QR-коду через тестовый API: QR-код
  со снимка экрана читается как `https://furkapp.net/tv/<код>`, ключ, отправленный на код, добавлен за секунду
  (экран входа) и обновил подписку («Сменить ключ» с тем же ключом); «Код устарел» → «Новый код», «Нет связи с
  furkapp.net» → «Повторить», после закрытия диалога запросы прекращаются; узкое окно и тёмная тема. Настоящий
  furkapp.net выдаёт код на 900 секунд и держит ожидание 10 секунд.
